Use **Settings** > **Player updates** to deploy signed Tilecast Player releases. Owners manage releases and the release source. Owners and Administrators can deploy updates. This updates the Player app; server, container, and operating-system updates have separate procedures.

## Release catalog

You do not need to prepare a release in a separate view before a normal deployment. **Deploy update** can download and verify the selected build for you.

Open **Release catalog** when you need release notes, verification details, manual uploads, cache management, or older versions. Choose **Android**, **Linux Legacy**, **Tilecast Edge**, or **Windows** with the **Player type** filter. Your filter and view stay in the URL, so bookmarks and browser navigation restore them.

<Steps>

1. Select **Sync releases** to refresh available Player builds from [Tilecast releases](https://github.com/gbyo/tilecast/releases). One coordinated release can contain Android, Edge, and Windows builds for the same version. See [Releases and downloads](../../reference/releases/).
2. Open a version to read its notes and inspect verification or cache state.
3. You can still select **Prepare artifact** manually, but deployment does not require this detour: **Deploy update** prepares an uncached verified build in the deployment flow.

</Steps>

Edge and Windows versions can have both **Intel / AMD 64-bit** (`x86_64`) and **ARM64** (`aarch64`) builds. The catalog groups those architectures under one version. Direct uploads remain separate entries.

If GitHub reports an error, the library keeps the releases it already has and shows the error. Use **Sync releases** to retry. Owners can open **More** > **Configure source** to configure GitHub's OAuth App client ID, connect with a device code, or disconnect a local connection. An environment-managed token must be changed on the server.

### Upload signed files directly

Open **More** > **Upload release**. Choose or drop the three files from the same signed release:

| Family        | Player file                              | Manifest                            | Signature                               |
| ------------- | ---------------------------------------- | ----------------------------------- | --------------------------------------- |
| Android       | `tilecast-player.apk`                    | `tilecast-player-update.json`       | `tilecast-player-update.json.sig`       |
| Linux Legacy  | `tilecast-player.AppImage`               | `tilecast-player-update-linux.json` | `tilecast-player-update-linux.json.sig` |
| Tilecast Edge | `tilecast-edge-<version>-<arch>.tar.zst` | `tilecast-edge-update.json`         | `tilecast-edge-update.json.sig`         |
| Windows       | `tilecast-windows-<version>-<arch>.msix` | `tilecast-windows-update.json`      | `tilecast-windows-update.json.sig`      |

Select **Upload and verify**. Transfer shows actual upload progress. Verification has its own waiting state, and the release becomes available only after the server verifies it.

Cache removal asks for confirmation and is unavailable while an active or paused deployment uses the release. A GitHub artifact can be downloaded again. A purged direct upload must be uploaded again.

## Deploy an update

<Steps>

1. Select **Deploy update** from either Player Updates view. You can also start from a build's **Deploy** action in **Release catalog**.
2. In **Update**, choose the **Player type** and **Version**. If that version has multiple CPU builds, choose **Intel / AMD 64-bit** (`x86_64`) or **ARM64** (`aarch64`). Tilecast automatically selects an unambiguous build when only one applies to the current fleet.
3. If the build is not cached yet, select **Prepare & continue**. Preparation runs on the server and shows progress; you can close the dialog and return later. If you leave it open, the workflow continues when the build becomes ready.
4. In **Targets**, search for screens or Display Groups. Add targets or use **Select all eligible**. Review the resolved screen count and warnings, then select **Continue**.
5. In **Rollout**, choose **Install now**, **Download only**, or **Maintenance window**. For a maintenance window, choose a future date and time in your browser's local timezone.
6. Open **Rollout safeguards** only when you need a canary cohort. Choose a size smaller than the eligible fleet; remaining screens wait until every canary succeeds.
7. Review the version, architecture, screen count, mode, and optional canary size. Select **Deploy update**.

</Steps>

You can go **Back** without losing your draft. Changing the Player type inside the deployment flow resets only choices that no longer apply.

Tilecast checks group membership, duplicate targets, Player family, architecture, and known Android SDK requirements before submission. Incompatible screen choices show the reason. A selected group containing an incompatible member blocks deployment and names the affected screen. Creation checks the current metadata again, so the preview is advisory.

Offline screens can receive queued commands after reconnecting, within the seven-day command expiry. Already-current screens receive no update command. They must be removed from a canary selection. **Download only** caches the artifact on the Player without requesting installation.

## Follow a rollout

**Deployments** opens by default. Work requiring intervention is separated into **Needs attention** before healthy **In progress** rollouts, with recent history below. The Deployments tab carries an attention badge, and selecting an attention row opens directly to the affected screens.

Select **View rollout** to inspect screens. Use **Needs attention**, **In progress**, **Finished**, or **All**, and search by screen name. Each screen shows its current and expected version, canary status, and last report. Downloading shows actual bytes and percentage; installation and reconnection show status without a percentage.

Failed and incompatible screens show their reported reason. **Retry** is available only for failed screens and only to Owners and Administrators. A screen waiting for permission or TV approval needs action at the display.

**Cancel deployment** asks for confirmation. It stops unfinished targets and leaves already-installed updates in place.

## Player limits

<Tabs syncKey="player-platform">

<TabItem label="Android TV">

The operating system may require local installation permission or approval on each TV. Plan for someone to handle the prompt at the display.

</TabItem>

<TabItem label="Linux">

Linux Legacy updates apply to Players running as a managed AppImage. Each Player restarts into the new version.

</TabItem>

<TabItem label="Tilecast Edge">

Choose the architecture reported by the Edge screen. Edge installs the release beside the current one, restarts into it, and keeps it only after it reconnects and shows content for two minutes. If it can't confirm the release, or loses power before confirmation, it returns to the previous release and reports failure.

An Edge update never requires pairing again. See [Update Tilecast Edge](../../edge/updates/) for rollback reasons and recovery.

</TabItem>

<TabItem label="Windows">

Choose the architecture reported by the Windows Player. Windows uses a signed MSIX package and must permit installation. The PC must trust the package publisher certificate. The deployment settles after the new Player reconnects and meets the health checks. See [Install Tilecast Player on Windows](../../players/install-windows/) and [Windows update troubleshooting](../../troubleshooting/player-updates/).

</TabItem>

</Tabs>

See the [Player update engineering contract](https://github.com/gbyo/tilecast/blob/main/docs/player-updates.md) for exact signed-file requirements, preflight rules, and deployment lifecycle.
