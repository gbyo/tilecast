---
title: Media uploads and processing
description: Diagnose media uploads, processing, storage, and playback-variant failures.
---

## An upload will not resume

If an upload was interrupted, select the original file again. It must have the same name and size as the file that started the upload.

Tilecast's resumable upload API tracks the accepted offset. A client that has lost that state must use the server's current offset rather than assuming where the transfer stopped.

## An item stays in processing

Open the asset and read the safe processing error. Tilecast Server needs writable media storage plus working FFmpeg and FFprobe executables.

Check `/readyz` when media infrastructure itself is unavailable. The production container includes the media tools and runs as an unprivileged user, so changing the whole server to root is not the normal repair.

Finalization is journaled. Keep the temporary/media volume and database row in place while Tilecast reconciles an interrupted move. Do not delete rows marked as finalizing while recovery is running.

## Storage is full

Tilecast reserves free space around media work. Free storage or reduce the upload size before retrying.

Preserve the database and `tilecast_data` media volume from the same point in time. Restoring only one can leave database records without files or unreferenced files without records.

## A Player cannot use a media item

The asset must be Ready and have a Player-compatible variant. A missing or corrupt downloaded object is rejected rather than promoted into playback.

Use [Activity](../../operations/activity/) to separate a server-side processing failure from a Player download or playback failure.
