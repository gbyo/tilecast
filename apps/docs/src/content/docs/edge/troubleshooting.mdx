---
title: Troubleshoot Tilecast Edge
description: Check local status and logs, and fix common pairing, playback, renderer, hardware, migration, and update problems on a Tilecast Edge Player.
---

Start in Studio. Edge reports through the normal Screens, Activity, and Player updates pages, so check those before you open a shell on the computer.

## Local status and logs

```sh title="On the Edge computer"
/opt/tilecast-edge/current/bin/tilecastctl status
journalctl -u tilecast-edge.service
journalctl -u tilecast-renderer.service
```

`tilecastctl status` shows pairing, the server connection, the renderer, safe mode, and recovery mode. The Player service and the renderer have separate logs, so you can tell a renderer crash from a Player problem. `tilecastctl capabilities` shows why a hardware feature is unavailable.

## Common problems

- **No server found:** enter the server address manually. LAN discovery is optional.
- **Presentation unavailable:** the content needs something Edge can't show, such as AirPlay Present, or it includes a Website or YouTube item while Edge's web helper is unavailable. Check [content compatibility](../compatibility/) and the [capability matrix](../capabilities/).
- **Live preview or Watch live shows a black area where a video plays:** Edge normally captures what the display shows, so video is included. Look in the renderer log for `preview:` lines: `journalctl -u tilecast-renderer.service | grep 'preview:'`. `using presented WPE buffer` is the normal source. `falling back to WebKit snapshot` means Edge couldn't read the display image, and the reason in brackets says why. A fallback image can leave out video. Playback itself isn't affected.
- **Renderer keeps restarting:** check Activity and safe mode before you delete any Player data.
- **The screen enters safe mode but the content looked fine:** read the Player log for `playback_stalled` and `heal_action` lines before the first recovery step. They name the content kind, the reason, the item, and the Layout zone when one applies, so you can see what Edge was waiting for. Edge doesn't treat a page, Widget, or Layout that stays unchanged as stalled. It recovers when a Layout zone that must keep updating stops, when a Website or zone never draws its first frame, or when a video stops advancing. Activity records the same reason on each recovery event.

  With the default reliability policy, video must show progress at least every 20 seconds, a new item has 90 seconds to produce its first render, and a rotating Layout zone has five minutes between required render evidence. Once playback is considered stalled, the recovery supervisor waits for the configured playback-stall threshold — three minutes by default — then tries **reactivate**, **reload renderer**, and **restart renderer**, spacing actions by 90 seconds. Repeated exhaustion of the full ladder enters Safe Mode after three ladder runs within one hour by default. Ten minutes of sustained healthy progress clears the recovery history. The organization or screen Player policy can change the stall threshold, restart window, restart count, and whether Safe Mode is enabled.
- **Display Control unavailable:** check the reason in `tilecastctl capabilities`, such as missing hardware, a missing permission, a disconnected display, no DDC/CI response, or an unsupported control. See [Display Control troubleshooting](../../troubleshooting/display-control/).
- **Migration refused or rolled back:** run `sudo /opt/tilecast-edge/current/bin/tilecast-edge-migrate status` for the reason, fix it, and migrate again. See [Migrate](../migrate/#automatic-rollback). The reason starts with the layer that failed:
  - `drm_probe_failed` means the display probe couldn't run. The text after it says why, such as `error while loading shared libraries`. Check the [requirements](../requirements/).
  - `drm_output_unavailable` means the probe ran but found no connected display with a mode.
  - `self_test_failed: renderer_start_failed` or `renderer_exited` means the test renderer didn't start or stopped. The text after it has the exit status or signal and the last line it printed. A message that mentions `bwrap` points to missing `bubblewrap` or blocked user namespaces.
  - `self_test_failed: fixture_import_failed` means the built-in test content couldn't be stored, for example because the disk is full.

## Before you reinstall or replace storage

If Edge is still reachable, collect status and logs before you restart or reinstall anything. Use Studio's **Player health**, **Activity**, and **Live preview** first, then `tilecastctl status` and the two service journals above. If playback is stuck but the daemon is healthy, try **Retry current item** or **Reload playback** from the screen's commands before restarting the Player.

Edge does not provide a supported export/import command for moving its local identity and content cache to another drive. The credential, state database, and verified content store are one local state set under `/var/lib/tilecast-edge/`; copying only part of that directory can leave an unusable or unsafe clone. The media cache is disposable and can be downloaded again.

For a failing SSD or USB device, install Edge on the replacement storage and use [Pair or replace a screen](../../screens/pair-and-replace/) > **Replace hardware for an existing screen**. The logical screen keeps its Display Group membership, assignments, schedules, policies, and history while the new Player receives a new device credential and downloads what it needs. Do not boot both an old cloned installation and its replacement with the same copied state.

If the same physical Player installation is still intact and only its credential needs repair, use **Repair existing credential** instead of hardware replacement.

## Share diagnostics safely

For a public issue, prefer bounded command output instead of copying Player state:

```sh title="Recent Edge logs"
 /opt/tilecast-edge/current/bin/tilecastctl status
 /opt/tilecast-edge/current/bin/tilecastctl capabilities
 journalctl -u tilecast-edge.service --since "30 minutes ago" --no-pager
 journalctl -u tilecast-renderer.service --since "30 minutes ago" --no-pager
```

Review the output for private hostnames, IP addresses, screen names, or content names before posting it. Do not upload `state.db`, the `identity/` directory, device credentials, pairing secrets, or the contents of `/var/lib/tilecast-edge/`. Preview backend logs do not contain pixel data or credentials.

A capture-backend problem and a renderer crash look different. If `tilecastctl status` says the renderer is healthy and the renderer journal has `preview:` messages such as `falling back to WebKit snapshot`, playback is alive and capture is degraded. If the renderer is disconnected, restarting, or the renderer service journal shows process exits, investigate the renderer failure first.

## Updates

```sh title="On the Edge computer"
sudo /opt/tilecast-edge/current/bin/tilecast-edge-update status
journalctl -u tilecast-edge-update.service -u tilecast-edge-update-guard.service
```

`status` shows the installed releases, the current one, and the last update with its result and reason. [Update Tilecast Edge](../updates/#when-edge-rolls-back) explains each rollback reason. For deployment problems in Studio, see [Player update troubleshooting](../../troubleshooting/player-updates/).

If the screen shows its recovery screen after an update and `tilecastctl status` reports `state_db_newer_schema`, follow [Recover after a rollback](../updates/#recover-after-a-rollback-to-an-older-state-database).

## Leftover 0.2.0 workaround files

If you worked around Edge 0.2.0 by hand with `edge-0.2.0-field-fix.conf` files in `/etc/systemd/system/*.service.d/`, Edge 0.2.1 removes them for you after an update is confirmed, but only the exact files that the Tilecast field script wrote. To see what is there:

```sh title="On the Edge computer"
sudo /opt/tilecast-edge/current/bin/tilecast-edge-update overrides
```

A file at one of those paths that you edited stays where it is, and the command lists it as an unknown override. Edge 0.2.1 ignores `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS`, so such a file can't turn the web sandbox off.

## What not to do

- Don't run `tilecastd` as root to work around a device permission.
- Don't delete `/var/lib/tilecast-edge/` as a routine troubleshooting step. It holds the screen's pairing and cached content.
- Don't post Player credentials, pairing secrets, or private state files in a public issue.
