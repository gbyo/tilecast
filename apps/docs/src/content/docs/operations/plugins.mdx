Tilecast plugins add optional features that ship with Tilecast. They are not downloaded from a third-party plugin store. Only an Owner or Administrator can install or remove a plugin.

The Forms, Countdown Bar, and Emergency Alerts listings include an icon and
screenshots of their configuration and display output. Select a screenshot
to view it larger. These images ship with Tilecast and need no external image
service. See the [plugin artwork contract](https://github.com/gbyo/tilecast/blob/main/docs/plugin-api.md).

## Install a plugin

<Steps>

1. In Studio, open **Operations** > **Plugins**.
2. Select **Explore** and choose a plugin to open its page.
3. Read the requirements and what the plugin can do, then select **Install**.
4. Open the plugin's page from the installed list and configure its instances.

</Steps>

Tilecast shows installed plugins and their setup state. Some plugins need a compatible Player or network connection. For example, **Emergency Alerts** needs the server to reach the National Weather Service. A listed requirement is guidance; installation itself does not confirm that a device meets it.

The built-in catalog includes:

| Plugin                                                  | What it adds                                                               | Important limit                                                              |
| ------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Countdown Bar**                                       | A timed bar over normal playback.                                          | Target Players must support plugin bars.                                     |
| **Emergency Alerts** <Badge text="US" variant="note" /> | Automatic response to matching National Weather Service alerts.            | Covers U.S. alerts and needs outbound server access to the NWS service.      |
| **Forms**                                               | Submission and approval workflows whose approved records can feed Widgets. | Forms are managed from their plugin page, not from the Data Sources library. |

## Marketplace listings

**Explore** shows every plugin as a card: built-in plugins, marketplace listings, and packages you added from GitHub. Each card shows the plugin's icon, name, who builds it, a short description, where it comes from, and whether it is installed, has an update, or does not support this release of Tilecast. Select a card to open the plugin's page. When the Marketplace has featured listings, they lead the page in a carousel. Searching or choosing a category or source hides the carousel so the results stay in focus.

**Explore** also shows marketplace listings next to the built-in plugins. Each listing names its publisher and version, states which Tilecast releases it supports, and links to its source repository. The Tilecast project reviews every listing before it appears; a listing is not a security review of the package.

Only an Owner or Administrator can install a listing, from its page, after reading what it adds and which releases it supports. Installed listings appear under **Extension packages** on the Installed tab. If a refresh fails, Studio says so and keeps showing the last available catalog. An Owner or Administrator can fetch the catalog again from the notice.

See the [marketplace contract](https://github.com/gbyo/tilecast/blob/main/docs/marketplace.md) for the catalog format and caching behavior.

## Custom repositories

An Owner or Administrator can add a package from any public GitHub repository with **Add from GitHub** on the **Explore** page. Studio looks up the repository's latest published release and shows a review before anything installs: the package identity and version, what it contains, the server capabilities it requests (network hosts, background jobs, storage, Studio interface), the pinned artifact digest, and the release provenance that verified it. Installing binds the repository to the package, so update checks re-resolve that same repository.

Custom entries are operator-chosen, not curated. Tilecast verifies the release provenance before installing, but adding a repository is still a trust decision: read the review and only install repositories you trust.

## A plugin's page

Every entry in **Explore** opens the same page, whether it is built in, from the Marketplace, or a custom package. The top shows the plugin's icon, name, and who builds it (**by Acme Signage**, or **by Tilecast** for built-in plugins). A publisher name links to the publisher's website for a built-in plugin, and to the package's repository for Marketplace and custom packages. A few badges say where it comes from, up to two categories, and whether an update is available. **Featured** appears only in **Explore**. The main action, such as **Install** or **Review & install**, is at the top right on a wide screen. On a phone or tablet it sits in the **Package status** card directly below the heading.

Below the heading the page covers:

- **Screenshots** from the plugin's listing, when it has any. Both built-in plugins and Marketplace listings can provide them. Swipe or use the arrows to browse, and select a screenshot to see it larger. The larger view shows which screenshot you are on (for example **2 of 4**) and has **Previous** and **Next** buttons; the left and right arrow keys work too, and **Esc** closes it. Nothing advances on its own, and the section is left out when a listing has no screenshots.
- **About**, a longer description of the plugin. It appears only when the plugin or Marketplace listing provides a longer description than the short one at the top of the page, so the same text never shows twice.
- **What this plugin adds**, such as Widgets and Data Sources, named by what they are rather than by file path.
- **Permissions & behavior**, which says in plain words whether the plugin connects to the network (and to which hosts), stores its own data on the server, runs background jobs, or adds its own settings interface. A plugin with none of these says so.
- **Requirements**, only when a plugin has requirements beyond the Tilecast release. A plugin that needs a newer release shows a notice at the top of the page and a disabled action instead.

The sidebar holds two cards. **Package status** leads with the current state, such as **Update available** with `1.3.0 → 1.4.0`, then the action that follows, then version and compatibility details. **About this package** shows the publisher, license, source, and links to the repository, documentation, and issue tracker. Built-in plugins say they are included with Tilecast and download nothing. Custom packages say they are not curated by the Marketplace. A collapsed **Technical details** section keeps the package ID, digest, registry, signer, and exact file paths for anyone who needs them.

A Marketplace package does not list what it adds or what it can do until you review it, because Tilecast reads that from the published package. Select **Review & install** to see it before anything installs. On a wide screen the review opens in a dialog; on a phone it opens as a sheet from the bottom. **Cancel** and **Install plugin** stay in view while you scroll.

Package capabilities are requests, not blanket host access. A server runtime that needs outbound network access declares the HTTPS hostnames it needs, and install or update review shows those hosts before activation. Storage, background jobs, Studio interface access, and Tilecast service grants are likewise bounded capabilities. An update can change those requests, which is why **Review update** calls out permission changes before you install the new version.

A capability in the package manifest is a request, not a self-granted permission. Server network access is limited to the HTTPS hostnames the package declares and Tilecast exposes to that package. The package does not receive the Tilecast Server's general network access or Player credentials. Storage, background jobs, and Studio interfaces are separate requested capabilities and are shown in the same review.

## Connect a plugin to another service

Some built-in plugins read from another system: a calendar, a point-of-sale catalog, or a device on your network. These plugins can't reach the network on their own. They use **connections** that you create, and Tilecast checks every request they send.

Before you install such a plugin, its page has a **Network connections** section, and a plugin that publishes data for screens has a **Data for screens** section listing the Data Sources it creates, whether it downloads pictures, and which fields hold personal data and for how long. In **Network connections**, for each connection it shows where the plugin sends requests, whether you choose that address, and what extra permission the connection could ask for. A connection that waits longer than 10 seconds or accepts responses larger than 1 MiB says so there too.

To set up a connection after you install the plugin:

<Steps>

1. Open the plugin's page from the installed list and select **Connections**.
2. Select **New connection**, give it a name, and, when Studio asks, enter its origin: the scheme, host, and port of the service, such as `https://calendar.example.org`. Don't include a path.
3. Select **Create connection**.
4. Choose the connection in the plugin's settings or in one of its items.

</Steps>

Only an Owner or Administrator can create, change, or delete a connection. Everyone who can see plugins can read a connection, but a connection never shows a password, a token, or another secret.

### Network permissions

A connection to something on your own network, such as a solar inverter or a library catalog server, can need extra permission. Each permission is a separate checkbox on the connection's page, with its own explanation, and saving the connection's name or origin never changes them.

- **Allow private network addresses** lets the connection reach addresses on your local network. Tilecast never reaches the Tilecast server itself, link-local addresses, or cloud metadata addresses, even with this permission.
- **Allow plain HTTP** lets the connection send unencrypted requests to its origin, and only to private addresses. Anyone on that network can read the traffic.
- **Allow secrets over plain HTTP** lets the connection send a stored secret, such as an API key, without encryption. It appears only when the plugin says it may need it.

Studio asks you to confirm before it gives a permission. Changing a connection's origin removes all of its permissions, so a permission you gave for one device never carries over to another. If a newer Tilecast release changes what a connection may do, Studio asks you to give the permissions again.

A connection that a setting or item still uses can't be deleted. Its page lists what uses it. See [Plugin connections](https://github.com/gbyo/tilecast/blob/main/docs/plugin-connections.md) for the exact address and redirect rules.

### Sign in to a provider with OAuth

Some connections sign in to an online account, such as a Google calendar or a Square catalog. Tilecast doesn't ship a shared sign-in app for these providers: you register your own OAuth client with the provider, and Tilecast keeps the tokens on your server. The install review lists the provider's sign-in address, its token address, and the access the plugin asks for.

Before you start, set `TILECAST_PUBLIC_URL` to the `https` address people use to reach Studio. Providers don't send a sign-in result to an unencrypted address, so Studio hides **Connect** and explains why until the address is `https`. See [Networking](/administration/networking/).

<Steps>

1. Create the connection as above. Its page shows a **Provider account** section.
2. Copy the **Redirect URI** from that section. In the provider's developer console, create an OAuth client (a "web application" client) and add this exact address as an authorized redirect URI.
3. Enter the provider's **Client ID** and, when the section asks for it, the **Client secret**, then select **Save client**. Tilecast stores the secret encrypted and never shows it again.
4. Select **Connect**. Sign in at the provider and approve the access it lists. The provider sends you back to the connection's page, which says whether the connection worked.

</Steps>

Tilecast renews access by itself. If the provider stops accepting the connection, for example because someone removed Tilecast's access in their account, the connection shows **Reconnect required**: select **Reconnect** and sign in again. If renewing fails for a moment, the page shows when it last failed and Tilecast keeps using the current access until it expires.

Select **Disconnect** to stop using the account. Tilecast asks the provider to revoke its access, when the provider supports that, and deletes its own tokens either way. The page tells you whether the provider confirmed. If it didn't, remove Tilecast's access in your account at the provider. A connected connection can't be deleted until you disconnect it. Changing the client ID also disconnects it.

A sign-in that takes longer than ten minutes, or that someone else started, doesn't finish. Select **Connect** again.

## Data that plugins publish

Some plugins publish data for your screens, such as a room's meetings or a menu. Each set of data is a **feed**, and each feed is an ordinary Data Source: choose it in a Widget like any other source. The plugin keeps it up to date. Open **Feeds** on the plugin's page to see each feed, when it was last published, how many records it has, and which Widgets use it.

If a plugin stops publishing for twice as long as it normally takes, the feed is marked late, and **Content Health** reports it like any other Data Source that stopped refreshing. It recovers on its own at the next publication.

### Change what a screen shows

Open a feed and select **View** on a record to see each field: the value from the provider, the value screens show, and whether you can change it. The plugin decides which fields you may change:

- **Provider only**: the value always comes from the provider. A price or an availability flag usually works this way, so a screen never shows a stale price.
- **Your value wins**: your value stays until you remove it, whatever the provider sends.
- **Yours until the provider changes it**: your value stays while the provider keeps sending the same value. When the provider changes that field, Tilecast removes your value, shows the new one, and the record says why.

Tilecast keeps the provider's values and yours apart, so removing your value always brings back the provider's. When a record disappears from the provider, your changes to it go too.

### Images from a provider

When a feed includes images, Tilecast downloads them itself after each publication, over HTTPS only, and stores them privately for the plugin. They never appear in your Media library, and a screen receives an image only while a current record uses it. An image that no record uses is deleted after 24 hours. If an image can't be downloaded, the record shows no image, the feed page says why, and the plugin shows a notice.

Feed images and records are part of your backups. A feed field that holds personal data, such as a meeting organizer, is deleted after the retention period the plugin declares; it stays in older backups until they expire.

## Check a plugin's status

A plugin that does work in the background, such as syncing a calendar every
few minutes, has a **Status** page. Open the plugin and select **Status**.

- **Plugin work** shows how many items wait and how many run now, and the
  last failure, such as "The plugin did not finish within 30 seconds."
- Tilecast retries a failed item with a growing delay. After eight failures
  it stops and lists the item under **failed 8 times**, so the plugin's other
  work continues.
- An Owner can **Retry** a failed item, which runs it again, or **Discard**
  it, which removes it for good. Other people see the list without these
  actions. Tilecast removes a failed item after 14 days.
- Work that waits for more than 7 days expires. The page counts expired
  items, because the plugin never received them.

Removing a plugin deletes its waiting and failed work.

### Events

Plugins can react to things that happen in Tilecast, such as a Takeover
starting or a screen going offline, and to events that other plugins
publish. A plugin that uses events also has a **Status** page:

- **Events this plugin receives** lists each event and who publishes it,
  Tilecast or another plugin. An event marked **Inactive** isn't delivered,
  and the row says why, for example that the publishing plugin isn't
  installed. Install that plugin and the event starts arriving on its own;
  events from before that are not delivered.
- **Events this plugin publishes** shows how many installed plugins receive
  each event. If a plugin update changed an event without giving it a new
  version, the event shows **Not published: the payload changed** and
  Tilecast stops publishing it, so other plugins never receive data they
  can't read. Update the plugin again, or ask its developer to publish the
  change as a new version.

Before you install a plugin, its page in the Store lists the events it
publishes and receives under **Events**. That list is for your information:
receiving an event doesn't give a plugin any other access.

### Webhooks

Some plugins receive requests from other systems: a provider telling the
plugin that something changed, or a device on your network reporting an
event. Those plugins have a **Webhooks** page with one card for each address.
Each card shows:

- the exact address to give the other system, with a copy button;
- whether it can work on this Server. A cloud provider can only reach a
  public HTTPS address, so set `TILECAST_PUBLIC_URL` to one. Tilecast can't
  test from the outside whether the provider really reaches it;
- the signing secret, when the provider signs its requests. Paste the
  provider's secret into the plugin's **Settings**; Tilecast shows only
  whether it's set;
- the last request it accepted, and the last one it refused and why.

For a webhook that uses tokens, select **Create token** and copy the token
right away: Tilecast keeps only a hash of it and can't show it again. Give it
to the sending system, which sends it as `Authorization: Bearer <token>`.
**Revoke** stops a token for good. Creating and revoking tokens needs the
**Manage plugins** permission.

The plugin's Store page lists its webhooks under **Webhooks** before you
install it, with how each one is checked and whether it needs a public HTTPS
address. Removing the plugin deletes its tokens and any requests it hasn't
handled yet.

## Manage installed packages

Open an installed marketplace or custom package from **Extension packages** to manage it:

- **Package status** shows what to do about updates. With no update known, **Check for updates** looks for one. When an update is available, the main action is **Review update**; select it to see the version change, what the update adds or removes, any permissions that change, and how the release was verified. A new network host or background job is therefore visible before you activate the update; updating is not an automatic permission expansion. **Update to 1.3.0** installs that exact version. After a check that finds nothing newer, the card says **Up to date**, and **Check again** is there if you want to look again.
- **Plugin settings** appears for a package that ships its own settings interface. It runs isolated from the Studio page and grows to fit its content, up to a limit; taller content scrolls inside it.
- **Background jobs** lists each scheduled job with its schedule, last result, and next run. A failed job shows a warning, how many times in a row it failed, and a short error.

Recovery and removal are at the bottom of the page, apart from everyday actions:

- **Package management** has **Restore previous version**, which returns to the last activation when one exists, after you confirm.
- **Danger zone** has **Remove package**, which deletes the installation and its contributions after confirmation. A custom repository binding survives, so the package can be reinstalled from **Explore**.

See the [package contract](https://github.com/gbyo/tilecast/blob/main/docs/packages.md) for the manifest format, provenance rules, and lifecycle behavior.

Removing a plugin is blocked while its instances or other plugin-owned resources remain. Remove those through the plugin's own page first. Removal does not delete those resources.

The same holds for extension packages: installing one adds its Widgets and Data Sources to the Studio libraries under the package name, and removing it is refused while any of those remain in use. Updating or restoring a version is refused only when the target version drops a Widget or Data Source that your content still uses, so content stays safe when the target version keeps the same contributions. The refusal names what still uses the package, so delete those Widgets and Data Sources first, then retry.

External Widgets preview inside an isolated frame in the Widget editor and Layout zones, using the same Widget contract as built-in previews. The package code never runs in the Studio page itself. See the [sandbox design](https://github.com/gbyo/tilecast/blob/main/docs/widget-sandbox-spike.md) for the isolation boundary and measurements.

You can also list, install, and remove plugins with `tilecast plugin` in the [command-line interface](../../integrations/cli/). Some installed plugins add their own CLI commands and MCP tools.

See [Configure Emergency Alerts](../emergency-alerts/) for coverage, matching rules, display modes, and poll health.

## Plugin changes during playback

Edge, Windows, and Android Players update plugin surfaces without restarting
the presentation when the manifest changes only plugin state. The current
playlist item and synchronized playback continue. If delivery fails, the
Player retries and keeps the previous committed manifest.

Changes to content, Layouts, Widgets, playback timing, or required resources
still use the normal presentation activation path. See the
[Player protocol](https://github.com/gbyo/tilecast/blob/main/docs/player-protocol.md)
for the exact refresh conditions.
