---
title: Add server behavior
description: Use Plugin API v1 Host services for routes, workers, status, removal checks, and core Tilecast resources.
---

Server code lives in the plugin directory and imports the Go Plugin SDK. It must not import `apps/server/internal`.

## Receive Host services

Implement `plugin.Initializer` when the plugin needs Tilecast services:

```go
func (p *Plugin) Init(_ context.Context, host plugin.Host) error {
    p.host = host
    p.db = host.DB
    return nil
}
```

`Host.DB` is for the plugin's own tables. Use the other Host services for core state.

Common services include `Installation`, `Audit`, `Manifests`, `Targets`, `Takeovers`, `ManagedPresentations`, `BackgroundJobs`, `Screens`, `Organization`, `Clock`, `Logger`, `DataSources`, `Users`, `PluginAssets`, and `Fonts`.

If a plugin needs a core table that is not represented by a Host service, don't query that table directly. Extend the API deliberately.

## Register HTTP routes

Implement `plugin.RouteProvider` and register routes below one of the manifest's `api.basePaths`.

Choose the access level that matches the endpoint:

- `AccessViewer` is for enrolled read-only `GET` and `HEAD` requests.
- `AccessManager` requires Owner or Administrator and CSRF on mutations.
- `AccessSession` requires an enrolled session and leaves resource-specific authorization to the plugin.

Use `plugin.PrincipalFrom` for the signed-in user and `plugin.DecodeJSON` for strict JSON requests.

Use `HandleWithRateLimit` with `plugin.RateLimitOperations` for an operation that needs the shared operations limiter.

Keep matching paths in `api/openapi.yaml`. `plugins:generate` composes the fragments into Tilecast's canonical OpenAPI document.

## Report status and removal blockers

`StatusReporter` supplies configured, active, instance-count, and attention state to the plugin catalog.

`RemovalGuard` runs inside the Remove transaction. Return blockers when the operator must delete, disable, or wait for plugin-owned resources before removing the installation row.

Removing an installation does not delete plugin data.

## Run background work

A `WorkerProvider` returns named workers. Automatic work should check the plugin installation and `Host.BackgroundJobs.Allowed()`.

The second gate pauses background changes during backup and restore. An explicit operator action does not use that gate.

Emergency Alerts is the current example of a networked background worker.

## Seed Demo Mode

Implement `DemoSeeder` when the plugin should add useful sample data to Demo Mode. Countdown Bar uses it to add a lunch countdown.

Keep demo seeding thin. It should use the same plugin behavior that normal product code uses.

## Use a connection (Plugin Manifest API 3)

A version 3 plugin sends HTTP requests through `http.fetch@1`. It names a connection record, usually the value of a `connection` field, and Tilecast checks the origin and every address, follows only approved redirects, and limits the body and the time.

```go
response, err := p.services.Fetch(ctx, plugin.HTTPRequest{
    Connection: uuid.MustParse(settings["calendar"].(string)),
    Method:     http.MethodGet,
    URL:        "/v1/events?limit=50",
    Headers: []plugin.HTTPHeader{
        {Name: "Accept", Value: "application/json"},
        {Name: "Authorization", Secret: &plugin.SecretHeader{
            Scope: plugin.ScopeOrganization, Key: "apiToken", Prefix: "Bearer "}},
    },
})
if plugin.IsServiceError(err, plugin.FetchPlaintextSecretRefused) {
    // The operator has not allowed a secret over plain HTTP.
}
```

- A path such as `/v1/events` works when the connection has one origin. Otherwise send the full URL.
- A `Secret` header names one of your own secret fields. Tilecast adds the value; your code never sees it.
- Failures are stable codes such as `origin_not_allowed`, `private_network_refused`, `redirect_refused`, `timeout`, and `response_too_large`. They never include resolver or TLS details.
- `npm run plugins:check` refuses `http.Client`, `net.Dial`, and similar calls in a version 3 plugin. Use `http.fetch@1` for provider traffic.

Test against `plugintest.Services` with a handler that answers `http.fetch@1/request`, so your tests never reach the internet.


## Keep state and schedule work (Plugin Manifest API 3)

Declare `storage.kv@1` to keep small values, such as a sync cursor, and `timers.schedule@1` (plus `timers.cancel@1`) to run code later. Don't create your own tables or goroutines for this.

```go
// A cursor survives restarts and reinstalls.
cursor, err := p.services.KVGet(ctx, "calendar:"+instanceID)
if errors.Is(err, plugin.ErrKVNotFound) {
	cursor = nil // start a full sync
}

// Store it only if nobody else moved it meanwhile.
swapped, err := p.services.KVCompareAndSet(ctx, "calendar:"+instanceID, cursor, next)

// Run HandleTimer again in five minutes. The same key replaces the old timer.
_, err = p.services.ScheduleTimer(ctx, "sync:"+instanceID, time.Now().Add(5*time.Minute), []byte(instanceID))
```

Implement `HandleTimer(ctx context.Context, timer plugin.Timer) error` on your plugin. Tilecast calls it with no signed-in person, for at most 30 seconds, and calls it **at least once**: after a crash or an error the same timer can run again, so make the handler safe to repeat. Returning an error retries the timer with a growing delay, from 5 seconds up to 15 minutes. After eight failed attempts Tilecast parks the timer: the plugin's **Status** page shows it, and an Owner can retry or discard it.

Limits: keys up to 128 bytes, values up to 64 KiB, 1 MiB of values per plugin, timer payloads up to 4 KiB, and 1,000 pending timers. Values are kept when the plugin is removed; removing the plugin deletes its pending timers. If you bump `definitionVersion`, Tilecast drops timers from the old definition, so schedule the ones you need again. See [Plugin storage and timers](https://github.com/gbyo/tilecast/blob/main/docs/plugin-storage.md) and [Plugin delivery](https://github.com/gbyo/tilecast/blob/main/docs/plugin-delivery.md) for every rule.

## Publish a feed (Plugin Manifest API 3)

Publish the complete set of records each time. Tilecast replaces the dataset and keeps operator changes according to each field's policy.

```go
revision, err := p.services.FeedRevision(ctx, "items", instanceID)
published, err := p.services.PublishFeed(ctx, plugin.FeedPublication{
	Feed:        "items",
	Instance:    instanceID,
	Replaces:    revision,
	Records:     []plugin.FeedRecord{{ID: "item-123", Values: map[string]any{"name": "Tea", "price": 3.5, "photo": "https://images.example.com/tea.png"}}},
	Connections: map[string]uuid.UUID{"images": imagesConnectionID},
})
if errors.Is(err, plugin.ErrFeedConflict) {
	// Another publication won. Read the revision again and retry once.
}
```

Use stable record IDs from the provider. A publication holds at most 2,000 records and 512 KiB. Tilecast fetches images after the publication commits; you never download image bytes yourself.
