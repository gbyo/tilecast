# Tilecast Edge: state and next work

This document is the implementation ledger for Tilecast Edge 1. It records what exists, what is proven, what is missing, and how to continue without breaking the architecture.

**Historical build sequence:** The M1–M12 plan used during initial Edge development is preserved in [`records/edge/edge-1-milestones.md`](records/edge/edge-1-milestones.md). It is not a current release checklist.

**Release and field status (2026-10-08):** Edge has published preview releases through `edge-v0.2.1-preview.1`. The [0.2.1 reliability review](tilecast-edge-sandbox-review.md) records hardware field problems and hardening. Preview releases and field tests are **not** general hardware-class or production qualification; the review requires verification on each deployment class. Check release notes, installed version, and device-specific qualification before migrating a production screen.

Read in this order:

1. [`tilecast-edge.md`](tilecast-edge.md): the Edge 1 architecture. It is binding. If a change must deviate from it, stop and write the complete tradeoff first.
2. [`apps/edge/AGENTS.md`](../apps/edge/AGENTS.md): fixed decisions and review rules for the code.
3. [`apps/edge/README.md`](../apps/edge/README.md): crates, dependency direction, build and test commands.
4. This document.

Work that is not part of Edge 1 is in [`tilecast-edge-future.md`](tilecast-edge-future.md). Do not start it from here.

## 1. Current state

### Native Player Core extraction

The [Core ownership contract](player-core.md) defines the extraction sequence.
The root workspace now has five shared Player crates.
`player-core` implements native selection, pairing, Server reconciliation,
manifest preparation, configuration acceptance, offline activation, command
delivery, Activity reporting, telemetry policy, and renderer recovery.
Edge calls these implementations.
The Core modules remain private. Hosts use the composition API and semantic types.
Edge retains Linux handlers, the migration hold, Runtime projection,
renderer adapters, private stores, and lifecycle. The
[readiness record](records/player-core-readiness.md) preserves the dated Core
extraction audit; current Edge qualification is recorded in the dedicated Edge
readiness documents.
The historical milestone records below use their original implementation names.
This extraction does not establish physical hardware qualification.

### 1.2 What a migrated screen does today

A migrated screen keeps its logical screen identity, Server binding, credential,
assignments, and history. It verifies the Server installation before sending
the credential, maintains the Player socket/heartbeat relationship, and plays
prepared content from local state through Server or WAN outages.

The shared Player Runtime renders native content, Layouts, Widgets, Websites,
YouTube, synchronized groups, and supported Span presentations. Remote web
content runs through the isolated `tilecast-web-renderer-wpe` helper. Invalid
or incompatible candidates never replace the last committed presentation.

Edge also provides durable commands, configuration, proof of play, telemetry,
live preview, Watch Live, Display Control, Presentation Network integration,
idle inhibition, and signed side-by-side updates with provisional confirmation
and rollback. The retired Noise Meter capture path is not part of current Edge.

Do not migrate a production screen until the signed release is qualified for
that screen's hardware class.

## 2. Invariants

These hold across every Edge release.

1. **One credential owner.** Only `edge-server` reads the device credential, and only `AuthenticatedServer` sends it. Obtain one only through `ServerClient::verify_installation`.
2. **Identity before credential.** Normalize the URL with `url_policy::normalize_server_url`, read `/api/v1/system/identity`, require the bound installation ID, then send the credential.
3. **Credential deletion.** Delete it only on `ServerError::CredentialRejected`. Never on a network error, 5xx or `screen_disabled`.
4. **The server is the only authority.** Server state arrives only from the authenticated server. Push events wake reconciliation; they never replace it.
5. **Offline first.** Readiness and playback never wait for the server. A failed reconciliation never replaces the last good state.
6. **Bytes are verified.** Every `BlobSource` feeds the content store, which checks size and SHA-256 before promotion. Add sources; do not add a second write path.
7. **The renderer holds nothing secret.** It gets content references for objects listed in the current activation and reports evidence. Everything else is in `tilecastd`.
8. **One-way migration.** Never modify or delete legacy files. No shadow mode, no dual runtime, no second credential.
9. **Health from evidence.** Supervisor decisions use meaningful playback evidence, not process or socket liveness.

## 3. Current readiness sources

Edge readiness is intentionally split by purpose instead of one ever-growing
milestone ledger:

- [Production readiness record](tilecast-edge-readiness.md) tracks subsystem
  readiness, hardening findings, and ranked implementation actions.
- [Hardware qualification procedure](tilecast-edge-qualification.md) defines
  the physical tests for display, media, remote web, Display Control, network,
  Span/synchronization, power/update behavior, and soak.
- [Production-readiness decision checklist](tilecast-edge-readiness-checklist.md)
  defines the criteria for making Edge the default Linux target and eventually
  discontinuing Linux Legacy.
- [Capability matrix](tilecast-edge-capabilities.md) describes what the current
  software implements and which paths still need hardware-class evidence.
- [Edge engineering records](records/edge/) preserve dated implementation
  reviews, spikes, and field evidence.

## 4. Current release status

As of 2026-10-08, signed Edge preview releases exist for x86_64 and aarch64,
including `edge-v0.2.1-preview.1`. A preview release proves packaging and the
checks recorded for that artifact; it does not automatically qualify a
different GPU, display path, Wi-Fi adapter, CEC/DDC device, or architecture.

The 0.2.1 hardening record documents failures seen on real Debian 13 Intel i915
screens and the fixes made afterward. Its field result is deliberately scoped:
the temporary-workaround 0.2.0 run is evidence for that screen, not stock 0.2.1
or a general hardware class.

## 5. Current next work

Use the ranked actions and blockers in
[tilecast-edge-readiness.md](tilecast-edge-readiness.md) and
[tilecast-edge-readiness-checklist.md](tilecast-edge-readiness-checklist.md).
Do not recreate the old milestone sequence in new PR descriptions.

The remaining work before broad production migration is evidence-driven:

- close any current software blockers in the readiness record;
- run the stock signed release through the hardware qualification procedure on
  every hardware class Tilecast intends to support;
- exercise migration, update, provisional power loss, and rollback on those
  classes;
- record long-running mixed-content soak results;
- keep no-SSH diagnostics sufficient for an administrator to understand and
  recover a field failure.

## 6. Validation entry points

From the repository root:

```sh
make edge-check
make edge-test
make edge-e2e
make docs-check
```

Run the narrower release, migration, update, renderer, hardware, and soak jobs
selected by the files changed. A current passing CI run is software evidence,
not a substitute for the physical qualification procedure.
